## Цели

После урока вы:

- **Общий минимум:** переводите бумажный дашборд М5.2 в спецификацию карточек Metabase (вопрос → SQL/агрегат → фильтр → подпись определения) на стеке **Metabase + Postgres**.
- **Аналитик:** собираете (или пошагово проектируете под будущий docker) дашборд диагностики Ритма: KPI сверху, разрезы, сырой слой; сверяете число контрольным SQL.
- **Продакт:** принимаете демо по чек-листу «решение / определения / нет свалки», а не по красоте виджетов.

---

## Контекст Ритма

**Провизорный стек курса:** локальный **Postgres** с синтетикой Ритма (`users`, `events`, `subscriptions`) + **Metabase** рядом (обычно `docker compose`). DataLens / Tableau — не инструмент студента; только опциональное чтение «как в другом BI».

На момент письма **живой docker может ещё отсутствовать**. Этот урок всё равно сдаётся: вы фиксируете спецификацию и чеклист подъёма. Когда compose появится — выполняете те же шаги без смены имён.

Вход: ваш wireframe из М5.2 (пример курса — диагностика недели: depth≥3, habit→check_in, ранний paywall, new Pro).

## Теория коротко

### 1. Бумага диктует BI, не наоборот

| На бумаге (М5.2) | В Metabase |
|---|---|
| Заголовок + if/then | Текст dashboard description / pinned markdown |
| KPI-карточка | Question (Metric/SQL) + описание определения |
| Разрез (воронка, когорта) | Question на dashboard с тем же фильтром периода |
| Сырой слой | Table question / SQL с `LIMIT` для сверки |
| Фильтр platform / неделя | Dashboard filter → поле или SQL-переменная |
| Отказ «нет MAU» | Просто не создаём; в description явный отказ |

Схема перевода: [`visuals/m5-4-paper-to-metabase.svg`](./visuals/m5-4-paper-to-metabase.svg).

### 2. Модель данных в Metabase

Минимум для Ритма:

1. Подключить Postgres (host/port/db/user из compose).
2. Синхронизировать схему; спрятать мусорные таблицы, если появятся.
3. Для учебных таблиц задать типы (даты как даты, `user_id` как Entity Key где уместно).
4. Предпочтительно: **SQL-вопросы** для KPI с нетривиальным определением (depth, когорты) — GUI-агрегат легко подменит зерно.
5. В описании каждой карточки — числитель / знаменатель / окно (как в М2.3).

### 3. Производительность и свежесть (учебный уровень)

- Не тащите сырой `events` на полный скан без фильтра даты в карточке мониторинга.
- Для диагностики недели ограничьте окно (например last 56 days) в SQL.
- На dashboard укажите ожидание freshness (< 36ч из М5.2) — даже если пока данные статичны.

### 4. Права (заготовка)

На учебном стенде достаточно одного admin. В спецификации всё равно напишите: кто редактирует определение KPI (аналитик), кто только смотрит (продакт/CEO-мониторинг).

## Разобранный пример: диагностика недели → 7 артефактов

Из М5.2 (рабочий вариант Б):

**Решение:** если depth≥3 < 25% две недели подряд → спринт на онбординг; иначе смотрим paywall.

| # | Карточка | Источник | Тип viz |
|---|---|---|---|
| 1 | Depth ≥3 (когорта last complete week) | SQL по `events` + `users` | number + сравнение к предыдущей |
| 2 | Habit → ≥1 check_in (7д) | SQL | number |
| 3 | Доля `paywall_view` с trigger до streak_3 | SQL по `props` | number |
| 4 | New Pro (users, `subscribe_started` / `subscriptions.started_at`) | SQL | number |
| 5 | Воронка install→…→subscribe | SQL или progress | funnel / bar |
| 6 | Когортная матрица D1/D3/D7 | SQL | table/heatmap |
| 7 | Сырое: onboarding без habit за 24ч | SQL table | table |

Фильтры dashboard: период (или «когорта недели install»), `platform`.  
**Нет:** MAU, store rating, цвет кнопки.

## Стенд: чеклист подъёма (когда docker готов)

Ориентир состава — [`visuals/m5-4-stack-checklist.svg`](./visuals/m5-4-stack-checklist.svg).

```mermaid
flowchart TD
  A[docker compose up<br/>Postgres + Metabase] --> B[Дождаться health<br/>Metabase UI]
  B --> C[Создать admin · подключить DB]
  C --> D[Проверить SELECT count(*)<br/>к users/events/subscriptions]
  D --> E[Собрать SQL-карточки по бумаге М5.2]
  E --> F[Dashboard: порядок KPI→разрезы→сырое]
  F --> G[Сверка 3 контрольных запросов]
  G --> H[Демо: if/then на факте чисел]
```

Пока compose нет — выполните шаги E–H как **спецификацию** (SQL в Markdown + порядок карточек + ожидаемые учебные числа из М2.3).

Провизорные порты/имена (замените, когда появится файл курса):

| Сервис | Ориентир |
|---|---|
| Postgres | `localhost:5432`, db `ritm`, user/password из `.env` |
| Metabase | UI на необычном порту (например `3001` / из compose), не конфликтовать с другими агентами |
| Данные | синтетика с теми же именами событий, что М4.3 |

Официальные практики вендора: [Metabase Learn — dashboard best practices](https://www.metabase.com/learn/metabase-basics/querying-and-dashboards/dashboards/bi-dashboard-best-practices).

## Практика

Опирайтесь на **свой** бумажный дашборд М5.2 (или эталон диагностики выше). Стек: Metabase + Postgres (факт или спецификация).

### Ядро (оба)

1. Перенесите бумагу в таблицу спецификации: карточка · определение · SQL-эскиз · viz · фильтр.
2. Напишите SQL-эскизы для **всех KPI верхнего ряда** (3–5) на схеме Ритма.
3. Опишите 2 dashboard-фильтра и 1 явный отказ (чего не будет).
4. Пройдите чеклист подъёма: отметьте `сделано` / `заблокировано: нет docker` / `спека готова`.
5. Три контрольные сверки (словами или SQL): count users в знаменателе depth; сравнение new Pro с `subscriptions`; sample 5 user_id из сырого слоя.

### Расширение «руки»

- Поднимите стенд (если доступен) и соберите dashboard физически; приложите скрин/экспорт вопросов.
- Если стенда нет: полный runnable SQL для карточек 1–4 + 7 в одном файле с CTE.
- Добавьте карточку freshness (`max(ts)` по events) и алерт-правило «если stale > 36ч — не принимаем решение».
- Оптимизация: покажите, где GUI Metabase опасен (например sum по строкам events) и почему оставлен SQL.

### Расширение «решение»

- Сценарий демо 10 мин: какие 3 предложения говорите, на какие числа опираетесь, что делаете при красном depth.
- Критерии приёмки дашборда для аналитика (чек-лист ниже + порог «не больше N виджетов»).
- Второй экран: 3-числовой мониторинг для CEO — отдельный dashboard, не вкладка-свалка.

## Критерии приёмки

- [ ] Спека карточек однозначно стыкуется с бумагой М5.2 (решение if/then сохранено).
- [ ] У каждого KPI есть определение в тексте карточки / спеки.
- [ ] Иерархия KPI → разрезы → сырое соблюдена.
- [ ] Есть 3 контрольные сверки; фильтры и список отказа заданы.
- [ ] Чеклист стенда заполнен (даже если docker ещё нет).
- [ ] Ядро + одно расширение.
- [ ] AI мог нагенерировать 20 чартов — вы оставили только связанные с решением.
