## Цели

После урока вы:

- **Общий минимум:** ведёте **словарь 5–7 метрик** Ритма, где у каждой одно число = одно определение (числитель, знаменатель, окно, зерно, исключения).
- **Аналитик:** различаете сырой поток, чистый слой, витрину и агрегат; знаете, что ломает backfill и смена схемы.
- **Продакт:** не принимаете «у нас конверсия 12%» без карточки определения; заказываете метрику так, чтобы три команды не получили три числа.

---

## Контекст Ритма

К демо прохода 2 на дашборде (М5.2 / М5.4) уже висят depth, воронка, когорты, Pro. Без словаря Metabase становится свалкой правдоподобных %, а спор «4% или 19%» из М2.3 возвращается на каждом синкапе.

Стенд: сырые `events` / `users` / `subscriptions` → учебные view (`v_depth_d7`, …) → карточки Metabase. Этот урок фиксирует **контракт смысла** до кликов по UI.

## Теория коротко

### 1. Три команды — три числа

Одна фраза «конверсия в Pro» без договора даёт:

| Команда | Тихий выбор | Число (учебное) |
|---|---|---|
| Маркетинг | install → subscribe, 30д | 3,8% |
| Продукт | habit → subscribe, 14д | 7,0% |
| Рост | paywall → subscribe, 7д | 19,0% |

Все три могут быть «правильными» SQL. Неправильна коммуникация без **артефакта определения**.

### 2. Определение как артефакт

Минимум полей карточки метрики:

| Поле | Вопрос |
|---|---|
| Имя | как называем вслух и в Metabase |
| Вопрос решения | какое if/then обслуживает |
| Зерно | user / день / подписка / событие |
| Числитель | событие / факт успеха |
| Знаменатель | кого считаем «в игре» |
| Окно | от какого якоря, сколько дней |
| Фильтры | `is_internal`, платформа, эксперимент |
| Дедуп / края | renew, дубли check_in, schema drift |
| Владелец | кто меняет определение |
| Версия / дата | когда зафиксировали |

Шаблон: [`visuals/m5-1-definition-card.svg`](./visuals/m5-1-definition-card.svg).

### 3. Слои: сырые → чистый → витрины → агрегаты

```mermaid
flowchart LR
  R[Сырые events/users/subs] --> C[Чистый слой: дедуп, типы]
  C --> M[Витрины: depth, воронка, когорты]
  M --> A[Агрегаты / карточки Metabase]
  A --> D[Решение на синкапе]
```

| Слой | Что лежит | Кто пишет | Риск |
|---|---|---|---|
| Сырой | факты как пришли | продукт / трекинг | грязь, drift (`local_date` vs `local_day`) |
| Чистый | те же факты, правила QA | аналитика | «почистили» без документации |
| Витрина | одна строка = один user×окно / шаг | аналитика | разные JOIN → разные % |
| Агрегат | KPI на дашборде | BI | число без ссылки на витрину |

Схема: [`visuals/m5-1-metric-layers.svg`](./visuals/m5-1-metric-layers.svg).

**Backfill:** пересчитали историю новым правилом — старые скриншоты врут. В словаре: «версия 2 с даты D; до D — v1».

**Смена схемы:** в грязном слое Ритма `schema_version` 1/2. Метрика, которая читает только `props->>'local_date'`, молча теряет часть check_in.

### 4. Словарь Ритма — стартовый набор (5–7)

Обязательный минимум курса (имена можно уточнить, смысл — нет):

1. **D7 habit depth ≥3** — доля users с `habit_created`, у кого ≥3 distinct дня с `check_in` в 7 дней от первого habit.
2. **Habit → ≥1 check_in (7д)** — ранняя активация.
3. **Habit → subscribe (14д)** — монетизация ценности (primary для многих решений P2/P4).
4. **Early paywall share** — доля `paywall_view` с триггером до `streak_3` (guardrail).
5. **Новые Pro** — users с первым `subscribe_started` / первой строкой `subscriptions` (без renew).
6. **Habit retention D7** — доля когорты с `check_in` на дне 7 (не путать с depth).
7. *(опционально)* **ARPPU периода** — выручка / платящие; mix month/year явный.

Каждая строка словаря = заполненная карточка из §2.

### 5. Связь с вехами

| Вехи / демо | Роль М5.1 |
|---|---|
| P1 | определения depth и воронки «запечатаны» |
| P2 | те же определения кормят лист экономики М1.3 |
| Демо-2 | дашборд М5.2/М5.4 ссылается на словарь, а не на «как получилось в SQL» |

## Разобранный пример: один % — две правды

Слайд: «Depth 48%».

| Версия | Знаменатель | Окно | Внутренние | Итог |
|---|---|---|---|---|
| A (маркетинг) | все install | любые 7 дней календаря | включены | ~«красиво» |
| B (курс) | users с `habit_created` | 7д от первого habit | `is_internal = false` | рабочее число P1 |

Обе могут считаться из Postgres. На демо прохода 2 принимается **только B**, потому что в словаре версия 1.0 так записана. Версия A — другая метрика с другим именем («calendar depth»), не «та же depth».

## Практика

Опора: воронка и четыре конверсии из [`m2-3-conversion-cohorts.md`](./m2-3-conversion-cohorts.md), древо из [`m1-3-unit-economics.md`](./m1-3-unit-economics.md), события [`m4-3-tracking-plan.md`](./m4-3-tracking-plan.md), стенд [`../stand/`](../stand/).

### Ядро (оба)

1. Соберите **словарь на 5–7 метрик** Ритма (таблица или Notion/Markdown).
2. Для каждой заполните все поля карточки §2 (даже если SQL ещё черновик).
3. Явно укажите **две метрики, которые чаще всего путают** (например depth vs D7 retention) и чем отличаются.
4. Добавьте колонку «источник слоя»: сырое / view / будущая витрина.
5. Зафиксируйте версию словаря: `ritm-metrics-v0.1`, дата, владелец.

### Расширение «руки»

- Для трёх метрик напишите псевдокод или черновик SQL (зерно user): depth, habit→subscribe 14д, early paywall share.
- Перечислите 3 способа сломать число на грязном слое стенда (дубли check_in, `local_day`, две строки subscriptions).
- Предложите QA-проверку: контрольный count строк до/после дедупа.

### Расширение «решение»

- Заказ аналитику: «нужна метрика X» в форме карточки — без созвона можно считать.
- Разберите конфликт: маркетинг хочет install→Pro на дашборде CEO. Что отвечаете? Какое *другое* имя даёте их метрике?
- Цена ошибки: если early paywall share считают как «доля users», а не «доля показов/триггеров» — какое ложное решение примете?

- [ ] 5–7 метрик с полными карточками; нет «голых» %.

- [ ] Ядро + одно расширение.
- [ ] AI мог нагенерировать глоссарий «как у всех SaaS» — вы выкинули метрики без якоря в событиях Ритма.

| Можно | Нельзя без вас |

| Черновик карточек и формулировок | Утвердить знаменатель и окно |

| Найти дубли имён в словаре | Решить, какая метрика primary для решения |
